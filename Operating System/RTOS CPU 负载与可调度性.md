# RTOS CPU 负载与可调度性

## Summary

RTOS 没有一个适用于所有系统的 CPU 负载上限。平均负载升高会压缩空闲时间，增加排队、响应抖动和截止期限违约的风险，但负载率本身不能证明多任务系统是否可靠。

工程上可以把**持续 70%** 当作开始分析的信号，把**持续 80%** 当作需要处理的告警，把**持续 90% 以上**视为几乎没有余量。它们只是缺少完整时序分析时的保守经验线，不是实时调度定理。硬实时系统即使只有 30% 的平均负载，也必须用任务的最坏执行时间和截止期限做可调度性分析。

单核周期任务的基础计算为：

$$
U = \sum_{i=1}^{n}\frac{C_i}{T_i}
$$

其中，$C_i$ 是任务的最坏情况执行时间，$T_i$ 是周期或最小到达间隔。固定优先级的速率单调调度可以先用 Liu-Layland 上界筛查：

$$
U \le n\left(2^{1/n}-1\right)
$$

任务数增加时，这个上界趋近于 $\ln 2 \approx 69.3\%$。它是充分条件：低于上界可以保证满足假设的任务集可调度，超过上界只代表这项快速测试无法下结论。此时应继续做最坏响应时间分析，而不是直接判定系统不可用。

## CPU 负载不等于实时性

CPU 负载描述一个统计窗口内处理器处于非空闲状态的时间比例。单核系统常用空闲任务的运行时间反推：

$$
U_{measured} = 1 - \frac{t_{idle}}{t_{window}}
$$

这个值适合观察趋势和发现容量压力，却没有表达任务在什么时候运行、被谁抢占、等待了多久，也没有表达截止期限。下面两个任务集说明了这种差别。

- 一个任务每 100 ms 运行 2 ms，CPU 利用率只有 2%。如果它必须在释放后 1 ms 内完成，那么它永远无法满足截止期限。
- 一组周期成谐波关系的任务可能在 95% 的理论利用率下仍然可调度，只是留给执行时间误差和额外中断的余量已经很少。

实时系统的直接判据是每个关键任务都满足：

$$
R_i \le D_i
$$

$R_i$ 是任务的最坏响应时间，$D_i$ 是相对截止期限。CPU 负载是容量指标，响应时间和截止期限才是时序指标。

## 多任务从多少负载开始受影响

只要处理器上有两个以上可运行任务，它们就会相互影响。高优先级任务会抢占低优先级任务，共享资源会产生阻塞，同优先级任务还可能轮转。工程上所说的「开始受影响」，通常指影响已经大到能被观测或可能破坏需求。

| 持续 CPU 负载 | 在缺少完整时序证明时的处理建议 |
| :--- | :--- |
| 低于 50% | 通常有较多余量，仍需检查硬实时任务的最坏响应时间 |
| 50% 到 70% | 观察峰值、ISR 时间、关键任务响应时间和队列积压 |
| 70% 到 80% | 进入分析区，新增功能前应重新计算时序预算 |
| 80% 到 90% | 进入告警区，短时突发和执行时间抖动容易暴露问题 |
| 90% 到 100% | 余量很小，软实时延迟通常明显上升，未经证明不应承载硬实时任务 |
| 100% 或更高的需求 | 长期需求超过处理能力，队列会持续增长或任务会错过期限 |

这张表是容量管理建议，不能代替调度分析。告警线还要根据业务后果调整：允许偶发延迟的遥测任务可以接受更高负载；电机控制、制动和保护任务不能靠平均负载判断安全性。

### 平均值会隐藏短时过载

假设 1 秒统计窗口的平均负载为 40%，其中某 10 ms 内所有任务同时释放并占满 CPU。平均图表看起来很轻，短截止期限的任务仍可能在这 10 ms 内超时。统计窗口越长，瞬时峰值越容易被平滑掉。

至少同时观察以下量：

- 每个关键任务的最大响应时间和截止期限违约次数。
- 周期任务的最大 CPU 时间、最大墙上时间和剩余裕量。
- 中断占用、最长关中断时间和调度延迟。
- 队列深度、高水位、丢包和积压恢复时间。
- CPU 负载的最大值、分位数和连续高负载时长，而不只看平均值。

RTEMS 的周期统计同时记录 CPU 时间和墙上时间。墙上时间包含任务等待资源以及被高优先级任务抢占的时间，更接近任务能否按期完成的问题。Zephyr 的 CPU Load 模块通过空闲入口和出口计算负载，并把中断上下文算入负载；Thread Analyzer 更适合观察线程运行分布。不同工具的统计口径未必一致，比较数据前要确认 ISR、空闲任务和调试任务是否被计入。

## 单核周期任务的理论上限

### 任务模型

经典分析用一个三元组描述周期或偶发任务：

$$
\tau_i = (C_i, T_i, D_i)
$$

- $C_i$：最坏情况执行时间，英文为 Worst-Case Execution Time，简称 WCET。
- $T_i$：周期任务的周期，或偶发任务的最小到达间隔。
- $D_i$：从任务释放开始计算的相对截止期限。

初步利用率应使用 WCET，而不是平均执行时间：

$$
U_{task} = \sum_{i=1}^{n}\frac{C_i}{T_i}
$$

还要把 ISR、内核、定时器、上下文切换和无法归入任务的后台开销算进去：

$$
U_{total} = U_{task} + U_{ISR} + U_{kernel} + U_{other}
$$

RTEMS 官方文档明确要求在放宽经典假设时计入 ISR、I/O、内核调用、资源等待和内存访问干扰。遗漏这些时间，会让纸面利用率低于真实需求。

### 固定优先级的快速充分测试

当系统满足以下条件时，可以使用 Liu-Layland 上界：单核、可抢占、任务相互独立、任务严格周期运行、$D_i = T_i$、执行时间有确定上界，并按周期越短优先级越高的速率单调规则分配优先级。

$$
U_{RM}(n) = n\left(2^{1/n}-1\right)
$$

| 任务数 $n$ | 充分保证上界 |
| ---: | ---: |
| 1 | 100.00% |
| 2 | 82.84% |
| 3 | 77.98% |
| 4 | 75.68% |
| 5 | 74.35% |
| 10 | 71.77% |
| 趋于无穷 | 69.31% |

这个上界回答的是：「只知道各任务的 $C_i$ 和 $T_i$，能否用一个简单不等式，对所有满足假设的任务集给出保证？」它没有声称 69.3% 以上无法调度。任务周期互为整数倍时，处理器理论上可以接近 100% 利用率。

如果截止期限不等于周期，优先级分配和分析方法也要调整。约束截止期限任务常用截止期限单调调度，即截止期限越短，优先级越高。此时不要直接套用只适用于 $D_i = T_i$ 的利用率上界。

### EDF 的 100% 边界

在 Liu 与 Layland 论文的理想单核模型中，最早截止期限优先的英文为 Earliest Deadline First，简称 EDF。它对隐式截止期限周期任务满足：

$$
\sum_{i=1}^{n}\frac{C_i}{T_i} \le 1
$$

这是该模型下的必要且充分条件。100% 表示理想调度模型的容量边界，不是推荐把实际设备长期跑满。真实系统仍要给中断、调度开销、缓存和总线干扰、WCET 估计误差及未来变更留出时间。

对 $D_i \ne T_i$、具有释放抖动、自挂起或共享资源的任务，简单的 $U \le 1$ 不再足够，需要使用处理器需求分析或对应任务模型的可调度性测试。

## 固定优先级系统用响应时间做最终判断

利用率测试失败后，固定优先级单核系统可以继续做最坏响应时间分析。忽略释放抖动时，任务 $\tau_i$ 的迭代式为：

$$
R_i^{(0)} = C_i + B_i
$$

$$
R_i^{(k+1)} = C_i + B_i +
\sum_{j \in hp(i)}
\left\lceil\frac{R_i^{(k)}}{T_j}\right\rceil C_j
$$

$B_i$ 是低优先级任务持有共享资源时造成的最大阻塞时间，$hp(i)$ 是所有高于任务 $i$ 的任务集合。不断迭代，直到结果不再变化，或者已经超过 $D_i$：

- 收敛且 $R_i \le D_i$，该任务通过测试。
- 任一任务出现 $R_i > D_i$，当前参数和优先级下不可调度。
- 所有关键任务都通过，才能得到任务集的时序保证。

有释放抖动时，干扰项通常还要加入高优先级任务的抖动 $J_j$。上下文切换、调度器和中断可以折算进任务执行时间，也可以建模为更高优先级的执行需求，关键是同一份开销不能遗漏或重复计算。

### 95% 利用率仍可调度的例子

下面三个任务按速率单调优先级调度，周期成整数倍关系：

| 任务 | $C_i$ | $T_i = D_i$ | 利用率 |
| :--- | ---: | ---: | ---: |
| $\tau_1$ | 2 ms | 5 ms | 40% |
| $\tau_2$ | 3 ms | 10 ms | 30% |
| $\tau_3$ | 5 ms | 20 ms | 25% |

总利用率为 95%，已经超过 3 个任务的 Liu-Layland 上界 77.98%。快速测试无法保证它可调度，响应时间分析仍可继续。

最高优先级任务的响应时间是 2 ms。第二个任务从 3 ms 开始迭代：

$$
\begin{aligned}
R_2^{(0)} &= 3 \\
R_2^{(1)} &= 5 \\
R_2^{(2)} &= 5\text{ ms}
\end{aligned}
$$

第三个任务从 5 ms 开始迭代，依次得到 10、12、17、19、19 ms，最终在 19 ms 收敛，小于 20 ms 的截止期限。因此，这组理想任务是可调度的。

最低优先级任务只剩 1 ms 的响应时间裕量。加入 1 ms 以上的额外中断、阻塞或 WCET 误差后，保证就会消失。理论可调度和工程上有足够余量是两个不同的问题。

## 如何计算工程上的合理上限

合理上限不是从 RTOS 名称或任务数量直接查表得到的。它来自任务模型、调度算法、硬件最坏条件和团队愿意承担的风险。

### 建立执行需求表

每个关键任务至少记录：

| 字段 | 含义 |
| :--- | :--- |
| $C_i$ | 在目标硬件和最坏路径上的 WCET |
| $T_i$ | 周期或最小到达间隔 |
| $D_i$ | 相对截止期限 |
| $B_i$ | 共享资源导致的最大阻塞时间 |
| $J_i$ | 释放抖动 |
| 优先级与 CPU 亲和性 | 决定抢占关系和处理器归属 |
| 关键等级 | 决定过载时哪些任务可以降级或丢弃 |

WCET 应在最低允许 CPU 频率、代表性的编译优化、最坏缓存与存储条件下评估。平均值、一次示波器测量或短时间压力测试不能替代 WCET 上界。

### 先算容量，再做时序证明

计算顺序可以保持简单：

1. 用 $\sum C_i/T_i$ 计算关键任务的 WCET 利用率。
2. 加入 ISR、内核、通信栈、DMA 或总线干扰等开销。
3. 用对应调度算法的充分测试做初筛。
4. 固定优先级系统对每个关键任务做响应时间分析，EDF 系统做对应的处理器需求分析。
5. 在压力、突发输入、最低频率和最长临界区下测量响应时间与截止期限违约。
6. 把功能增长和测量误差留成独立余量，不要把所有空闲时间提前分配掉。

若只能做早期容量估算，可以写成预算式：

$$
U_{target} \le U_{analysis} - U_{unmodeled} - U_{growth}
$$

$U_{analysis}$ 是所用充分测试允许的容量，或精确分析得到的最大可调度需求；$U_{unmodeled}$ 留给尚未建模的中断、内核与硬件干扰；$U_{growth}$ 留给功能增长和参数漂移。

初期无法可靠量化后两项时，保留 20% 到 30% 的 CPU 时间是常见的保守做法。因此，固定优先级硬实时系统在缺少精确分析时，把目标负载放在 60% 到 70% 通常比追求 80% 更稳妥。这个范围是工程策略，安全等级、WCET 可信度和过载后果不同，余量也应不同。

### 用缩放因子求任务集的理论极限

若想求一个具体任务集在当前优先级下还能增长多少，可以对所有可伸缩执行时间乘以负载因子 $q$：

$$
C_i' = qC_i
$$

逐步增加 $q$ 并重复响应时间分析，找到所有任务仍满足 $R_i(q) \le D_i$ 的最大值 $q_{max}$。对应的利用率就是该模型下的任务集上限：

$$
U_{max}^{model} = q_{max}\sum_{i=1}^{n}\frac{C_i}{T_i} + U_{fixed}
$$

$U_{fixed}$ 表示不会随业务执行时间同比增长的固定开销。实际发布上限还应低于 $U_{max}^{model}$，两者之间的差值用于覆盖建模误差和运行环境变化。

这个缩放方法适合估算统一的性能退化或业务增长。若只有某个通信任务会增长，应该只缩放该任务；若 ISR 到达率会变化，则应调整 ISR 的最小到达间隔。把所有任务一起缩放，可能掩盖真实的局部热点。

## 阻塞、中断和调度开销怎样计入

共享互斥量会让高优先级任务等待低优先级任务。Sha、Rajkumar 与 Lehoczky 的优先级继承研究指出，直接使用普通同步原语可能造成无界优先级反转；优先级继承和优先级上限协议可以约束阻塞。响应时间公式中的 $B_i$ 必须来自所用锁协议及最长临界区，不能凭平均锁等待时间估算。

ISR 对所有任务形成更高优先级干扰。周期中断可以按执行时间和最小到达间隔建模：

$$
U_{ISR} = \sum_{k=1}^{m}\frac{C_{ISR_k}}{T_{ISR_k}}
$$

偶发中断应使用最小到达间隔，突发中断还要描述一次突发内可能出现的最大次数。只统计 RTOS 任务运行时间而漏掉 ISR，CPU 负载和时序预算都会偏低。

调度器、Tick、软件定时器、跟踪日志和上下文切换也消耗 CPU。可以测量每次操作的最坏开销，再按最坏发生频率换算为利用率。调试日志尤其容易改变时序，测量版本与发布版本的配置差异要记录清楚。

## 多核系统不能把核数直接乘进去

具有 $m$ 个同构核心时，$\sum C_i/T_i \le m$ 只是总容量的必要条件之一。任务亲和性、迁移、每核中断、共享缓存、内存总线和跨核锁都会影响可调度性。某个核心达到 100% 时，其他核心的空闲时间未必能被固定在该核心上的任务利用。

常见分析方式有两类：

- 分区调度把任务固定到核心，对每个核心分别做单核分析，还要处理跨核共享资源。
- 全局调度允许任务迁移，需要使用与具体全局调度器匹配的多处理器分析。

Zephyr 的 SMP 文档允许用 CPU Mask 固定线程可运行的核心；RTEMS 也区分全局、集群和具有亲和性的 SMP 调度器。多核 RTOS 的合理上限应按每核负载、任务映射和共享资源一起计算，不能把单核的 69.3% 或 EDF 的 100% 直接乘以核心数后当作保证。

## 常见误区

### 把 69.3% 当成固定优先级的绝对上限

69.3% 是任务数趋于无穷时的通用充分保证，不是不可调度边界。超过它之后继续做响应时间分析，很多任务集仍然可以得到保证。

### 用平均执行时间代替 WCET

平均执行时间适合估算能耗和常态吞吐量。硬实时分析关心的是最坏路径，它可能来自缓存未命中、罕见协议分支、Flash 等待、总线竞争或最长临界区。

### 只看总 CPU，不看低优先级任务

高优先级任务即使按时完成，也可能把低优先级任务压到长期得不到运行。应同时检查各任务的响应时间、饥饿、队列积压和截止期限违约。

### 把测试通过当成时序证明

测试只能覆盖已经出现的路径和输入。硬实时保证还需要一个可信的最坏执行时间上界、明确的到达模型和与实际调度器一致的分析。

### 忽略频率和低功耗状态

动态调频会改变相同代码所需的墙上时间，深度睡眠还会增加唤醒延迟。CPU 负载百分比没有自动表达这些变化，分析时应使用最低允许频率和最大唤醒延迟。

## 实用决策流程

发现 CPU 负载升高时，可以按以下顺序处理：

1. 确认测量口径，包括统计窗口、空闲任务、ISR、调试任务和每核数据。
2. 查看关键任务的最大响应时间、剩余裕量与违约次数。
3. 用 WCET、最小到达间隔和截止期限更新任务模型。
4. 重新运行利用率测试和响应时间分析。
5. 检查最长 ISR、最长关中断区、锁阻塞和队列高水位。
6. 若分析不通过，缩短执行路径、降低到达率、拆分临界区、调整优先级或任务映射。
7. 保留未建模开销和功能增长余量，再确定发布告警线。

在没有完整模型时，持续 70% 适合作为分析触发线，持续 80% 适合作为告警线。已有严格可调度性证明的系统，应以最小截止期限裕量和模型适用条件作为主要门槛，CPU 百分比退回到运行监控指标的位置。

2. Mathai Joseph, Paritosh Pandya, [Finding Response Times in a Real-Time System](https://doi.org/10.1093/comjnl/29.5.390), 1986。提出固定优先级系统的最坏响应时间求解方法。
3. Lui Sha, Ragunathan Rajkumar, John P. Lehoczky, [Priority Inheritance Protocols: An Approach to Real-Time Synchronization](https://doi.org/10.1109/12.57058), 1990。分析优先级反转、优先级继承与优先级上限协议。
4. RTEMS Project, [Rate Monotonic Manager: Background](https://docs.rtems.org/docs/6.1/c-user/rate-monotonic/background.html)。给出利用率规则、首个截止期限规则、周期统计，以及放宽经典假设时需要加入的开销。
5. RTEMS Project, [CPU Usage Statistics](https://docs.rtems.org/docs/6.1/c-user/cpu_usage_statistics.html)。说明 RTEMS 的任务 CPU 时间统计口径及其精度限制。
6. Zephyr Project, [CPU Load](https://docs.zephyrproject.org/latest/services/debugging/cpu_load.html)。说明基于空闲时间的负载测量，以及与 Thread Analyzer 在中断统计上的区别。
7. Zephyr Project, [Symmetric Multiprocessing](https://docs.zephyrproject.org/latest/kernel/services/smp/smp.html)。介绍 SMP 线程迁移、CPU Mask 和每核调度相关行为。
8. FreeRTOS, [Run Time Statistics](https://www.freertos.org/Documentation/02-Kernel/02-Kernel-features/08-Run-time-statistics)。介绍如何统计每个任务实际运行的绝对时间和处理器时间百分比。
